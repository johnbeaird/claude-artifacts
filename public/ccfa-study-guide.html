The CCFA is a closed-book, scenario-driven exam aimed at people who actually run Falcon — not theory people. CrowdStrike wants to know whether you can deploy sensors, configure policies, manage users, and read the console without freezing up. The questions reward operational fluency over textbook recall.

What follows is organized by the sixteen domain areas CrowdStrike publishes, with the high-yield concepts in each, the places people lose points, and a short critical-distinctions section at the end for the things that get conflated under pressure.

Domain 01 · User Management & RBAC

Roles, permissions, and API keys

Knowing the canned roles cold and how custom roles compose are the bread and butter here.

  • Falcon uses Role-Based Access Control (RBAC). Built-in roles include Falcon Administrator, Falcon Analyst, Falcon Investigator, Endpoint Manager, and the Real Time Response role family.
  • Roles can be scoped to specific host groups — a user can be admin over one fleet and read-only on another.
  • API keys are managed under Support and resources → API Clients and Keys. Each client has its own scopes; keys can be rotated and revoked.
  • 2FA is required for human users; service accounts use API client credentials, not 2FA.
  • You can clone an existing role to start a custom one — faster than building from scratch.
⚠ Watch your six

If a user needs to read files on a compromised host but should not be able to extract them, the right role is Real Time Responder — Read Only Analyst, not Active Responder. Read Only Analyst gets a narrow command set (cat, cd, ls, ps, reg, filehash, etc.) — no get, no put, no killing processes.

Domain 02 · Sensor Deployment

Installation, prerequisites, and the troubleshooting that follows

The exam will hand you broken installs and ask you to diagnose. Know the install flags by feel.

  • OS prerequisites matter: each OS has a supported kernel/version matrix. Falcon will refuse to install on unsupported kernels and goes into Reduced Functionality Mode (RFM) on partially supported ones.
  • Default provisioning window: a fresh sensor has 20 minutes to phone home to the CrowdStrike cloud (10 minutes on Falcon 6.21 and earlier). If it can't reach cloud in that window, the sensor uninstalls itself.
  • You can override the provisioning window at install time with --provisioning-token + ProvNoWait=1 or by extending the timeout (e.g., ProvWaitTime on Windows).
  • Linux uses falconctl to license/configure the sensor. macOS requires Full Disk Access granted to the Falcon package before licensing.
  • To verify the Windows sensor is running: sc query csagent. The service name is CSAgent; the process is CSFalconService.exe.
Domain 03 · Host Management & Setup

Filtering hosts, RFM, and the inactive sensor lifecycle

Operational page-navigation questions live here. Know the filters and the timelines.

  • Host Management filters include: hostname, group, OS version, sensor version, last seen, OU (Active Directory Organizational Unit), health events, detections, preventions. Username is not a filter.
  • Inactive sensor lifecycle: a host that hasn't checked in for 7 days moves from Host Management to the Trash page. It stays in Trash for 90 days before permanent deletion. Restoring works if it checks back in during that window.
  • Reduced Functionality Mode (RFM) is when the sensor is installed but can't fully operate (unsupported kernel, missing FDA, etc.). Detections and prevention are limited; the host is still visible but flagged.
  • Disabling detections on a host suppresses new detections but does not remove existing ones — useful for known-good systems generating noise.
⚠ Watch your six

To find sensors that haven't checked in recently: Host setup and management → Managed endpoints → Inactive Sensors, then set the time range. The Sensor Report widget will get you there too, but the dedicated Inactive Sensors view is the canonical answer.

Domain 04 · Host Groups

Static vs. dynamic group membership

  • Static groups: you explicitly add/remove hosts. Predictable, manual.
  • Dynamic groups: membership is rule-based — host attributes (OS, OU, tag, hostname pattern) determine inclusion. Membership re-evaluates automatically.
  • A host can belong to multiple groups, and policies attach to groups. When multiple policies match, precedence on the policy assignment list breaks the tie (top wins).
  • Best practice: keep group purposes narrow and orthogonal (by OS, by environment, by criticality) so policy mapping stays auditable.
Domain 05 · Prevention Policies

Toggles, sensitivity, and what's actually blocking

Prevention policies are where Falcon decides what to stop, not just detect. Sensitivity sliders are exam-favorite material.

  • Prevention policies have separate slider groups for Cloud Anti-Malware, Sensor Anti-Malware, Behavior-Based Protection, Execution Blocking, and more — each with a sensitivity level and a detection-or-prevention toggle.
  • Slider values: typically Disabled, Cautious, Moderate, Aggressive, Extra Aggressive. Higher = more false positives.
  • Each toggleable feature has two independent settings: Detect (alert only) and Prevent (block + alert). You can detect without preventing.
  • Like sensor update policies, the Default Prevention Policy is the catch-all when no other policy matches a host's groups.
  • Changes propagate to sensors during their next check-in (~few minutes), not instantly.
Domain 06 · Custom IOA Rules

When the built-in detections aren't enough

Custom Indicators of Attack (IOAs) let you describe behaviors that should trigger detection or prevention, beyond CrowdStrike's stock library.

  • Rule types include Process Creation, File Creation, Network Connection, Domain, DNS, and more — each with type-specific fields.
  • Actions per rule: Monitor (log only), Detect (alert), Kill Process (the closest to "block" — kills the offending process).
  • Rules live inside rule groups; rule groups are assigned to prevention policies. Assignment flow: rules → rule group → prevention policy → host group.
  • Pattern syntax uses regex-style wildcards. To match a domain and all its subdomains: *.baddomain.xyz|baddomain.xyz — the pipe lets you match the bare domain too.
  • Custom IOAs can block via network/domain — useful when IOC management can't (see Domain 13).
Domain 07 · Sensor Update Policies

Version pinning and uninstall protection

  • Three update strategies: Latest Sensor Version, N-1 (one version behind latest), N-2 (two versions behind), or a specific pinned version.
  • Uninstall and Maintenance Protection: when enabled, uninstalling or running maintenance commands on the sensor requires a maintenance token generated from the console. Prevents unauthorized or accidental removal.
  • Tokens can be one-time or bulk-generated; they're tied to the AID (Agent ID) or to the customer.
  • The Default Sensor Update Policy is the catch-all — it applies to any host not matched by another policy. Often set to "latest" or "N-1" depending on org risk tolerance.
⚠ Watch your six

The "Default" qualifier appears on both Sensor Update Policies and Prevention Policies. The exam will quiz you on which Default is the catch-all for what — read the question carefully.

Domain 08 · Response Policies & Real Time Response

Three RTR roles, three command tiers

Real Time Response (RTR) is the remote-shell capability into a host. Roles gate the command set; response policies gate what RTR can do on a given host.

  • RTR — Read Only Analyst: diagnostic commands only. cat, cd, clear, env, eventlog, filehash, getsid, help, history, ipconfig, ls, mount, netstat, ps, reg. No file removal, no process kill.
  • RTR — Active Responder: all Read Only commands plus active ones — get (pull a file), put, kill, rm, runscript, memdump, restart. Can take action.
  • RTR — Administrator: everything Active Responder gets, plus visibility into all analyst sessions and the ability to manage custom scripts and Put files. Use for IR leads and audit.
  • Response policies sit alongside prevention policies and define what RTR features are enabled on the host (sessions, command logging, queued commands, custom scripts).
Domain 09 · Containment

Network containment, not full quarantine

  • Network containment isolates a host: only Falcon traffic and explicitly allowlisted IPs can reach the host. Everything else is blocked.
  • You can allowlist IPs for containment exemptions (e.g., your jump box, your patching infrastructure). Configure in containment policy.
  • Containment is reversible — release the host from the console and traffic flows resume.
  • Containment is a policy: hosts must be in a group with containment enabled, and a user with the right role must trigger it. Don't confuse containment with quarantine of a file.
Domain 10 · Exclusions

When you need Falcon to ignore a path

  • Three exclusion types: Sensor Visibility Exclusions (sensor stops reporting events from this path), Machine Learning Exclusions (ML detections are suppressed for this path), IOA Exclusions (Indicators of Attack are skipped here).
  • Exclusions are powerful — they reduce visibility. Scope them to the narrowest path possible and avoid wildcards that catch too much.
  • Path syntax supports wildcards: * matches anything in a path segment; ** matches across segments.
  • Exclusions are scoped to host groups, not global by default. Always check assignment before assuming an exclusion is live.
Domain 11 · Firewall Policies

Managing the host firewall through Falcon

  • Falcon Firewall Management lets you control the native host firewall (Windows Defender Firewall, etc.) from the Falcon console.
  • Policies have rule groups with inbound/outbound rules; rule precedence is top-down within a policy.
  • You can enforce or monitor: Enforce mode pushes rules to the host firewall; Monitor mode logs what would have been blocked without changing the host firewall state.
  • Rule actions: Allow, Block, Monitor. Test in Monitor before flipping to Enforce.
Domain 12 · Quarantined Files

Where blocked files go to wait

  • When Falcon prevents a malicious file, it's quarantined — moved to a protected location on the host where it can't execute, and a record is created in the console.
  • From the Quarantined Files page: Release (restore the file — for false positives), Delete (permanent), or Download (pull a copy for analysis).
  • Downloads are password-protected ZIPs by default to prevent accidental execution. Default password: infected (verify in your tenant).
  • Quarantine retention is configurable — files don't sit there forever.
Domain 13 · IOC Management

What IOCs can — and cannot — do

This is the highest-value gotcha in the entire exam. Burn it in.

  • Indicators of Compromise (IOCs) in Falcon are limited to two actions: Detect only and No action. You cannot block via IOC management.
  • IOC types: SHA256, MD5, IPv4/IPv6, Domain. Files (hashes) can be blocked via Prevention policy hash blocklists; network IOCs cannot block via IOC management at all.
  • If you need to block an IP or domain, use a Custom IOA rule with action "Kill Process" on a Network Connection or Domain rule type (see Domain 6).
  • IOCs are tenant-wide; they apply across all hosts unless scoped via platform/host filtering.
⚠ Watch your six — exam-favorite

"How do you block traffic to baddomain.xyz?" The wrong answer is "create an IOC." IOCs only detect on network indicators. The right answer is "create a Custom IOA with a Domain rule." Memorize this distinction.

Domain 14 · USB Device Control

Allow, block, audit removable storage

  • USB Device Control policies restrict use of USB mass storage and other USB devices by class, vendor, product, or serial.
  • Modes: Full Block, Read-only, Allow. You can combine with exception rules for specific vendor/product IDs.
  • Risk dashboards under USB Device Control surface which hosts have plugged in what — useful for IR and audit.
  • Like other policies, USB Device Control is assigned to host groups with the Default policy as catch-all.
Domain 15 · Dashboards & Reports

Sensor Report, audit logs, scheduled reports

  • Common reports: Sensor Report (deployment health, versions, inactive sensors), Detection Activity, Prevention Policy, User Audit, API Audit.
  • Audit logs separate user activity from API activity. Both are queryable and exportable.
  • Reports can be scheduled with email delivery — useful for compliance evidence and weekly leadership digests.
  • Custom dashboards: add widgets from a library (detection trends, sensor versions, top processes blocked, etc.) and pin to your home view.
Domain 16 · Workflows

Automated responses to triggers

  • Falcon Fusion Workflows are trigger-action automations: a detection or condition fires, the workflow runs predefined steps.
  • Trigger types: detection generated, host enters a group, sensor health event, schedule, manual launch.
  • Action types: send notification (email, webhook, ticketing), contain host, update tag, run RTR script, call an API.
  • Workflows have conditions and branches — you can route based on severity, tactic, hostname pattern.
  • Test workflows before turning them on for production — a misfiring containment workflow will isolate prod servers fast.

★ The critical distinctions

Concepts the exam will try to conflate

These are the high-confusion pairs. If you only memorize one section of this guide, make it this one.

IOC vs. IOA. Indicators of Compromise are artifacts (hashes, IPs, domains) — Falcon's IOC management can only detect on them, not block. Indicators of Attack are behaviors (a process tree pattern, a domain reach-out) — Custom IOAs can kill the process. When the question is "how do I block X," it's almost always Custom IOA, not IOC.

Detect vs. Prevent. Every protection feature has two switches. Detect generates an alert. Prevent blocks the activity and generates an alert. A feature can be on in one mode and off in the other. The question "the sensor is alerting but not stopping the file" is asking about this distinction.

Containment vs. Quarantine. Containment isolates a host from the network. Quarantine moves a file to a protected location. They're entirely separate concepts; the exam will pair them in answer choices to trip you up.

RFM vs. inactive. Reduced Functionality Mode is a sensor with degraded protection (usually OS/kernel related) but still checking in. Inactive is a sensor that isn't checking in at all. Both appear on Host Management but mean different things.

Default Sensor Update Policy vs. Default Prevention Policy. Both are catch-alls for their respective policy types. They are distinct policies with distinct settings. The exam will phrase questions ambiguously — read for context (update version pinning → Sensor Update; ML sensitivity → Prevention).

Read Only Analyst vs. Active Responder vs. Administrator (RTR). Read Only sees but cannot act. Active Responder can act on a host (kill, get, put, run). Administrator can see everyone else's RTR sessions. If the question is about audit/oversight, it's Administrator. If it's about reading without changing, it's Read Only.

★ Prep strategy

Where to actually spend your time

1. CrowdStrike University, Falcon Administrator Learning Path. The official courseware is the closest thing to the exam by design. Work through every module; don't skim. The labs reinforce muscle memory for console navigation, which the exam tests indirectly through scenario phrasing.

2. Hands-on console time, ideally in a test tenant. Six months in production is the official recommendation for a reason — the exam describes workflows the way an admin does them, not the way a textbook explains them. If you don't have a tenant, ask Trace3 about access to a partner environment.

3. The official CCFA Certification Exam Guide. Download from CrowdStrike University. It's brief but lists every domain CrowdStrike commits to testing. Treat it as a checklist.

4. Practice tests — but pick carefully. Several Udemy courses and ExamTopics-style sites have practice questions. Use them to surface gaps in your knowledge, not as a primary source. The unofficial dumps often have outdated answers (Falcon UI moves quickly) — verify anything that surprises you against the official docs.

5. Time-box your sittings. 60 questions in 90 minutes is 90 seconds per question — comfortable for most, tight if you over-think. Practice at speed before exam day.
